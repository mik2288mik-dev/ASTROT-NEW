# LUMIA → Android (Google Play + RuStore) — план выпуска

> Статус: ПЛАН (до старта работ). Сейчас приложение — Telegram Mini App (Next.js web).
> Цель: выпустить то же приложение на Android в Google Play и RuStore, по всем правилам.
> Дизайн/картинки готовит пользователь отдельно — здесь только инженерия и комплаенс.

---

## 0. TL;DR (сразу главное)

- **Стратегия:** не переписывать на нативку, а **обернуть существующий web в Capacitor** (нативная оболочка + плагины биллинга/пуша/auth). Кодовая база уже частично готова к мультиплатформе (поля `platform`/`auth_provider`/billing `provider`/`channel`/`app_version` заведены в Фазе 0–6 админки).
- **3 самых дорогих/обязательных блока** (без них в сторы не пустят):
  1. **Авторизация** — заменить «только Telegram initData» на реальный вход (Google Sign-In / email; Telegram остаётся для мини-аппа).
  2. **Платежи** — Premium через **Google Play Billing** (Play) и **RuStore Billing** (RuStore). Telegram Stars в этих сторах нельзя.
  3. **Приватность/право** — Privacy Policy, **удаление аккаунта в приложении + веб-URL**, Data Safety (Play), возрастной рейтинг, для RU — **152-ФЗ (локализация перс. данных в РФ)**.
- **Срок:** полноценный двойной запуск с платежами и пушами — **≈ 6–10 недель** фокусной разработки. Минимальный бесплатный Android-врап без покупок — **≈ 2–3 недели**.
- **Главные внешние блокеры (нужны решения/аккаунты от тебя):** Google Play Developer ($25), RuStore-аккаунт (для РФ — обычно юрлицо/ИП), решение по 152-ФЗ (российский хостинг для данных РФ-пользователей), Firebase-проект (FCM), текст Privacy Policy (желательно с юристом — у нас чувствительные данные: дата/время/место рождения).

## 1. Стратегия упаковки

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Capacitor (рекомендую)** | один web-код, нативные плагины (billing, FCM, auth, deep links), оба стора | нужен Android-проект + плагины | **выбираем** |
| TWA / Bubblewrap (PWA) | проще всего | нет нормального IAP/Play Billing, слабый контроль | нет (платежи не закрыть) |
| React Native / Flutter (нативный рерайт) | максимально «нативно» | переписать весь UI — месяцы | нет (нецелесообразно) |

Capacitor даёт: WebView с нашим Next.js, доступ к нативным API через плагины, сборку `.aab` (Play) и `.apk`/`.aab` (RuStore).

## 2. Что менять в приложении (архитектура)

### 2.1 Авторизация (`auth_provider` уже заведён)
- Сейчас: вход только через подписанные Telegram `initData`. Вне Telegram это не работает.
- Нужно: добавить провайдеры — **Google Sign-In** (Android, нативный плагин) и/или **email-вход** (+ 2FA для админки). Telegram остаётся для мини-аппа.
- Сервер: `lib/auth/appAuth.ts` уже абстрагирует `provider`; добавить верификацию Google ID-token + сессии. Гостевой режим оставить для «посмотреть без входа».

### 2.2 Платежи (`payments`/`subscriptions` + `provider` уже заведены)
- Сейчас: Telegram Stars (`star_payments`, provider=`telegram_stars`).
- Нужно:
  - **Google Play Billing** (подписки Premium) + серверная валидация покупок (Google Play Developer API) + обработка **Real-time Developer Notifications (RTDN)** через Pub/Sub.
  - **RuStore Billing SDK** + серверная валидация + вебхуки RuStore.
  - Единый контракт `subscription_event` (purchase/renew/cancel/refund) → в таблицу `subscriptions` (уже спроектирована). Цена/триал/статус — provider-agnostic.
- Важно (правило сторов): цифровые товары (Premium) ОБЯЗАНЫ идти через биллинг стора. Нельзя вести на внешнюю оплату/Stars из Android-сборки.

### 2.3 Пуши (`channel` уже заведён)
- Сейчас: уведомления уходят через Telegram-бота (ретеншн-движок).
- Нужно: **FCM (Firebase Cloud Messaging)** для Android (и RuStore push / тоже FCM). Хранить device push-token на юзере; ретеншн-движок шлёт в FCM для платформы `android`, в Telegram — для `telegram`. `notification_logs` уже есть.
- Разрешение `POST_NOTIFICATIONS` (Android 13+) — запрашивать в рантайме.

### 2.4 Версионирование / совместимость
- `app_version` (уже в users) + feature flag **`min_app_version`** (уже создан в Фазе 6) → экран «обнови приложение». Maintenance-mode флаг тоже есть.

### 2.5 Геокодинг/локация
- Город рождения — через автокомплит (без GPS). **Разрешение на геолокацию НЕ нужно** (это упрощает Data Safety и ревью). Не добавлять location-пермишены без явной нужды.

## 3. Требования Google Play (правила, которые надо закрыть)

- **Аккаунт разработчика** ($25 единоразово) + верификация личности/организации (Google ужесточил — нужны документы; для нового аккаунта-организации требуется D-U-N-S и т.п.).
- **Privacy Policy URL** — обязателен (у нас перс. данные, включая чувствительные: дата/время/место рождения). Разместить публичную страницу.
- **Data Safety форма** — задекларировать: какие данные собираем (имя, дата рождения = «приблизительная геолокация/иное?», платежи, аналитика), передаём ли третьим (OpenAI для генерации — задекларировать!), шифрование, удаление.
- **Account deletion (КРИТИЧНО):** Google требует:
  - удаление аккаунта/данных **из приложения** (мы строим user-facing «Удалить аккаунт» — сейчас удаление есть только в админке, нужно добавить в Settings пользователя);
  - **публичный веб-URL** для запроса удаления данных (без установки приложения).
  - У нас в админке уже есть `data_deletion_requests` концепция — связать.
- **Target API level** — таргетить свежий Android API (на 2026 — обычно API 35/«latest−1»), иначе не примут/перестанут показывать.
- **Play App Signing** — включить (Google хранит ключ).
- **Content rating (IARC анкета)** — астрология/гороскопы: вероятно 3+/Teen; в описании добавить дисклеймер **«для развлечения, не является медицинским/финансовым/юридическим советом»** (у нас уже есть анти-эзотерик/анти-медицина правила в контенте — это плюс на ревью).
- **Permissions** — минимум: `INTERNET`, `POST_NOTIFICATIONS`. Никаких SMS/контактов/локации/камеры без нужды.
- **Subscriptions** — настроить продукты Premium в Play Console, описать условия, авто-продление, отмену.
- **Ads** — нет; в Data Safety отметить отсутствие рекламных ID, если не используем.

## 4. Требования RuStore (РФ)

- **Аккаунт RuStore** — для монетизации обычно нужно **юрлицо/ИП** (самозанятость ограниченно). Подтверждение через Госуслуги/ЭЦП.
- **152-ФЗ (КРИТИЧНО для РФ):** персональные данные граждан РФ должны **храниться и обрабатываться на серверах в России**. Сейчас БД на Railway (вне РФ). Варианты: российский хостинг/БД для РФ-пользователей, либо разделение данных по региону. Требует инфраструктурного решения. Возможна регистрация **оператора ПД в Роскомнадзоре**.
- **Privacy Policy** на русском + согласие на обработку ПД (галочка при регистрации/онбординге).
- **Возрастная маркировка** (0+/6+/12+/16+/18+) по 436-ФЗ. Астрология обычно 12+/16+.
- **RuStore Billing SDK** — свои покупки (не Google Billing). Серверная валидация.
- **RuStore push** — можно через тот же FCM или RuStore SDK.
- Контент-правила RuStore (нет запрещёнки) — у нас ок.

## 8. Что УЖЕ сделано в коде в пользу мультиплатформы

- Поля `platform` (telegram/ios/android/web), `auth_provider`, `app_version`, `country` на `users` и событиях (миграции Admin v2).
- Провайдер-агностичный биллинг: таблицы `payments`/`subscriptions` + `provider` (telegram_stars сейчас; app_store/google_play/stripe — заделы).
- `channel` (push/in_app/email) для коммуникаций; единый ретеншн-движок.
- Feature flags `min_app_version`, `maintenance_mode` (Фаза 6) — для принудительного обновления и техработ.
- Канон event-таксономии с property `platform`/`app_version`.
- Учёт всех пользователей (telegram + web-guest) в аналитике (events для гостей включены).

Это снижает объём интеграции на этапах B/C/D — абстракции на месте, нужно подключить реальные провайдеры.
