# Задача: единый персональный экран «Сегодня / Неделя / Месяц / Год»

## Цель

Полностью заменить текущую систему главного персонального прогноза на один продукт с четырьмя периодами:

- Сегодня;
- Неделя;
- Месяц;
- Год.

Во всех вкладках прогноз строится по натальной карте конкретного пользователя и рассчитанным влияниям выбранного периода. Общие прогнозы по знаку не должны использоваться внутри этого экрана и остаются только в отдельном продукте «Зодиак».

GPT-4.1 не вычисляет астрологию и не придумывает жизненные события. Сервер рассчитывает, классифицирует и передаёт факторы, а модель только объясняет их обычным человеческим языком.

## Критическая проблема текущей реализации

Сейчас:

- «Сегодня» использует personal daily canvas;
- «Неделя / Месяц / Год» на Dashboard загружают общие sign horoscopes;
- структура тем у периодов различается;
- несколько карточек получают одинаковые или повторяющиеся фоны;
- один и тот же фон может появляться в соседних вкладках и создавать впечатление копии экрана.

После выполнения задачи все четыре вкладки используют единый контракт, единую навигацию и одну визуальную систему с разными периодическими наборами изображений.

## Единая продуктовая структура

В каждом периоде ровно семь постоянных тем:

1. Твой день / Твоя неделя / Твой месяц / Твой год
2. Любовь
3. Работа и дела
4. Деньги
5. Настроение и силы
6. Общение
7. Удача

Дополнительно сервер выбирает 2–3 динамические темы по реальной силе расчётных факторов выбранного периода.

Динамические темы обновляются по ключу периода:

- день — новая локальная дата;
- неделя — новая ISO-неделя;
- месяц — новый календарный месяц;
- год — новый календарный год.

Не менять темы искусственно. Если длительное сильное влияние сохраняется, одна и та же динамическая тема может повториться. Новизна используется только как небольшой tie-breaker между почти равными кандидатами.

## Доказуемость расчёта

Каждый рассчитанный фактор получает стабильный `evidence_id`.

```ts
export type CalculatedAstroEvidence = {
  id: string;
  kind:
    | 'transit_to_natal'
    | 'transit_house'
    | 'lunation'
    | 'ingress'
    | 'station'
    | 'period_aggregate';
  transitPlanet?: string | null;
  natalPoint?: string | null;
  aspect?: string | null;
  house?: number | null;
  orb?: number | null;
  status: 'applying' | 'separating' | 'exact' | 'active' | 'unknown';
  exactAt?: string | null;
  startsAt?: string | null;
  endsAt?: string | null;
  strength: number;
  polarity: 'supporting' | 'challenging' | 'mixed' | 'neutral';
  topicKeys: Array<FixedForecastTopicKey | DynamicForecastTopicKey>;
  calculationSource: string;
};

export type TopicEvidence = {
  primary: CalculatedAstroEvidence[];
  supporting: CalculatedAstroEvidence[];
  conflicting: CalculatedAstroEvidence[];
  confidence: 'high' | 'medium' | 'low';
};
```

Модель возвращает только ID использованных evidence. Сервер проверяет ID и формирует точные названия планет, аспектов, орбисы и периоды из рассчитанного пакета. Модель не может добавить новый аспект или изменить орбис.

## Расчёты по периодам

### Сегодня

Использовать натальную карту, транзиты конкретной даты, транзит→натал аспекты, активированные дома, орбисы, applying/exact/separating и период действия. Быстрые влияния допустимы. Время суток называть только при реальном расчёте в часовом поясе пользователя.

### Неделя

Рассчитывать весь семидневный интервал. Объединять один продолжающийся аспект в одно окно, учитывать даты входа, точности и выхода, длительность и повторяющиеся факторы. Положение Луны одного случайного дня не может определять всю неделю.

### Месяц

Рассчитывать весь календарный месяц. Группировать длительные транзиты, учитывать точные даты и повторные прохождения, значимые лунации, ингрессии и станции только при наличии реального расчёта. Не делить месяц искусственно на недели.

### Год

Рассчитывать весь календарный год. Выделять длительные транзит→натал влияния и их пики, объединять прямые и ретроградные повторные попадания. Ежедневные лунные колебания не использовать как основу года. Не обещать брак, развод, увольнение, доход, болезнь, переезд или покупку.

## Распределение факторов по темам

До вызова GPT сервер обязан:

1. Рассчитать evidence выбранного периода.
2. Назначить evidence допустимые темы.
3. Рассчитать вес для каждой темы.
4. Сформировать `TopicEvidence` для семи постоянных тем.
5. Выбрать 2–3 динамические темы по порогу силы.
6. Не создавать третью тему при недостаточном основании.
7. Не использовать один главный evidence как единственное основание нескольких карточек.
8. Передавать модели только evidence конкретной темы.

## Системный промпт

```text
Ты пишешь пользовательский контент приложения «Твой Гороскоп».

Твоя задача — понятно объяснять уже рассчитанные астрологические данные.
Ты не вычисляешь положения планет и не добавляешь факты от себя.

Порядок ответа:
1. Сразу ответь на вопрос темы.
2. Объясни, что показывает совокупность переданных факторов.
3. Кратко объясни астрологическое основание в отдельном поле.

Используй только evidence, переданные для конкретной темы.
Не придумывай события, разговоры, покупки, задачи, конфликты,
партнёра, работу, людей или обстоятельства жизни пользователя.

Не заменяй прогноз психологическим портретом.
Не давай нравоучений и не добавляй совет автоматически.
Не увеличивай текст ради заполнения поля.
Когда ответ закончен — остановись.

Пиши обычным современным русским языком.
Без эзотерики, пафоса, коучинга, сленга и псевдопсихологии.
```

## Task-промпт темы

```text
Напиши персональный прогноз для указанной темы и периода.

card:
- коротко ответь, что показывает расчёт;
- не создавай интригу, hook, CTA или искусственный заголовок.

reading:
- расскажи прогноз по переданным evidence;
- объясни совместное действие primary, supporting и conflicting факторов;
- не придумывай жизненную сцену;
- не давай обязательный совет;
- даты и части периода называй только при наличии в evidence;
- при слабой выраженности темы скажи это коротко и не заполняй поле пустотой.

astrology.explanation:
- объясни, почему факторы дали такой вывод;
- используй понятные названия планет, домов и аспектов;
- не добавляй факторы, отсутствующие во входе.

astrology.evidence_ids:
- верни только ID из переданного списка;
- максимум четыре наиболее важных ID.

Запрещены пустые формулы и их перефразировки:
«день неоднозначный», «спокойный фон», «темп снижается»,
«период требует ясности», «лучше закончить начатое»,
«держись за главное», «не распыляйся», «энергия дня»,
«ритм дня», «внутренний фокус», «главная задержка».

Минимальной длины нет. Заверши ответ сразу, когда вопрос раскрыт.
```

Инструкция overview зависит от периода:

- day — рассказать, как будет проходить день;
- week — как будет развиваться неделя и когда меняется акцент;
- month — как будет развиваться месяц и какие рассчитанные окна его определяют;
- year — главная персональная картина года и периоды усиления.

Не создавать AI-generated `hero_title`, `hero_hook`, `focus`, `chance`, `risk`, `advice`, `context`.

## Ограничения текста

Только потолки:

- `card`: 280 символов для любого периода;
- day reading: 700 символов;
- week reading: 900 символов;
- month reading: 1100 символов;
- year reading: 1400 символов;
- astrology explanation: 500 / 650 / 750 / 900 символов соответственно;
- максимум 4 evidence на тему;
- `meaning`: 240 символов.

Короткий законченный ответ проходит валидацию.

# Визуальный контракт фонов и картинок

## Главный принцип

Одинаковый контентный каркас не означает одинаковый визуальный экран.

У каждого периода должна быть своя визуальная семья:

- day — живее, ближе, оперативнее;
- week — композиции с направлением и несколькими связанными элементами;
- month — более широкие редакционные сцены и крупные формы;
- year — самые цельные и выразительные hero-композиции.

Это одна дизайн-система, но не четыре копии одной картинки.

## Что запрещено

- один и тот же `asset.path` дважды на одном экране;
- один и тот же hero во вкладках day/week/month/year;
- один и тот же фон темы «Любовь» во всех четырёх периодах;
- назначение всем карточкам одного `visualSection` ради удобства;
- повтор картинки после переключения вкладки, когда в пуле есть альтернатива;
- случайный выбор, из-за которого фон меняется при каждом рендере;
- растягивание одной картинки разным crop и выдача этого за новый фон;
- генерация ежедневных картинок через LLM/API;
- использование картинки, не оставляющей читаемую область под текст.

## Новый visual resolver

Создать отдельный периодический resolver:

```ts
export type ForecastVisualRequest = {
  userId: string;
  period: PersonalForecastPeriod;
  periodKey: string;
  topicKey: FixedForecastTopicKey | DynamicForecastTopicKey;
  slot: 'hero' | 'fixed' | 'dynamic';
  slotIndex: number;
};

export type ForecastVisualAssignment = {
  assetId: string | null;
  path: string | null;
  textSide: 'left' | 'right' | 'center';
  backgroundPosition: string;
  paletteTag: string | null;
};
```

Resolver должен:

1. Использовать `period + topicKey + periodKey + userId` как детерминированный seed.
2. Назначать изображения всему экрану одним проходом, а не каждой карточке независимо.
3. Выбирать без повторения `asset.path` внутри экрана.
4. При равных вариантах избегать изображения, использованного этой темой в предыдущем периоде.
5. Сохранять выбор стабильным в течение периода.
6. Не хранить визуальный выбор в GPT-ответе: GPT не выбирает изображения.
7. Разрешать смену изображения без перегенерации текста.

## Манифест

Расширить manifest метаданными:

```ts
periods: Array<'day' | 'week' | 'month' | 'year'>;
topicKeys: Array<FixedForecastTopicKey | DynamicForecastTopicKey>;
paletteTag: string;
compositionTag: string;
```

Нужны отдельные пулы:

- hero_day, hero_week, hero_month, hero_year;
- fixed topic pools для каждого периода;
- dynamic topic pools по смыслу темы.

Текущий набор имеет около двух вариантов на многие темы и не способен дать четыре визуально разные вкладки. Агент должен:

1. Провести инвентаризацию всех существующих WebP/SVG.
2. Не копировать один файл под новыми именами.
3. Подключить все реально разные существующие изображения.
4. Сформировать точный список недостающих asset slots для последующей отрисовки.
5. Пока слот не обеспечен уникальной картинкой, использовать качественный периодический CSS/texture fallback, а не повтор чужой картинки.

CSS fallback должен быть частью дизайн-системы: светлый редакционный фон, текстура, крупная геометрическая форма, без мистики и без случайных цветов. Он временный и явно помечается в диагностике `visualFallback: true`.

## Проверки визуального выбора

Добавить тесты:

- на одном экране нет повторяющихся asset path;
- hero четырёх периодов различаются при достаточном пуле;
- выбор стабилен для одного periodKey;
- новый periodKey может менять фон;
- одна тема не получает один и тот же asset во всех периодах при наличии альтернатив;
- исчерпание пула даёт CSS fallback, а не повтор;
- текстовая сторона и background position соблюдаются;
- динамические темы получают подходящий topic pool.

## UI

Единый экран:

- вкладки `Сегодня / Неделя / Месяц / Год`;
- большая hero-карточка текущего периода;
- сетка шести постоянных тем;
- горизонтальная лента 2–3 динамических тем;
- `card` показывается на карточке;
- внутри: `reading` → «Почему такой прогноз» → «Показать расчёт»;
- никаких AI-заголовков, hooks, CTA и эмодзи;
- при смене периода обновляются текст, period label, динамические темы и визуальная семья;
- скелетон сохраняет размеры карточек и не вызывает скачков экрана.

## Монетизация

Не менять платёжную систему. Сохранить возможность:

- overview периода полностью free;
- короткие `card` видны всем;
- одна постоянная тема может быть free;
- остальные reading, динамические темы и подробный расчёт — Premium.

## Кэш

Единый key builder учитывает:

- user/chart id;
- period;
- periodKey;
- timezone;
- chart calculation version;
- prompt version;
- voice version;
- unified model id.

Считать несовместимыми старый daily canvas, старые personal period extras и sign-based week/month/year на личном Dashboard. Не удалять кэш отдельного раздела «Зодиак».

Визуальные назначения имеют отдельную версию `visualManifestVersion` и не требуют перегенерации GPT-текста.

## Prewarm

- day: текущий день и после вечернего порога следующий;
- week: текущая неделя и ближе к концу недели следующая;
- month: текущий месяц и ближе к концу месяца следующий;
- year: текущий год; следующий год только в конце текущего года;
- не генерировать неделю, месяц и год ежедневно заново.

## Fallback

Не показывать общий прогноз по знаку или выдуманный текст при ошибке. Вернуть `generating`/`unavailable`, диагностический код и кнопку повтора.

## Обязательные тесты

1. Личный Dashboard не вызывает sign horoscope endpoints.
2. Все периоды содержат ровно семь постоянных тем.
3. Dynamic содержит 2–3 темы по порогу силы.
4. Prompt не требует бытовых сцен и разрешает отдельное астрологическое объяснение.
5. Короткий законченный ответ проходит.
6. Evidence ID ответа входят во вход темы.
7. Даты в тексте существуют в evidence.
8. Старые кэши несовместимы только для личного forecast screen.
9. UI отображает card/reading/explanation/evidence.
10. Визуальный resolver не повторяет фон на одном экране.
11. Typecheck, unit tests и production build проходят.

## Definition of Done

- один персональный продукт для day/week/month/year;
- общие sign horoscopes удалены из личного Dashboard;
- семь одинаковых постоянных тем и 2–3 расчётные динамические темы;
- GPT-4.1 только объясняет evidence;
- нет выдуманных сцен, обязательных советов и псевдоязыка;
- отдельное астрологическое объяснение и точные факторы;
- четыре периода имеют разные визуальные семьи;
- ни одна картинка не повторяется на одном экране;
- старые текстовые fallback не попадают пользователю;
- тесты, typecheck и production build зелёные;
- итоговый отчёт содержит изменённые файлы, финальные промпты, JSON-схему, cache migration, visual asset inventory, список недостающих картинок и реальные риски.
