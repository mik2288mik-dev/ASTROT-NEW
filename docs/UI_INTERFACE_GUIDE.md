# UI Interface Guide

Этот файл — общий стандарт работы с интерфейсом приложения. Используй его не только для полного дизайн-аудита, но и для любой задачи, где меняется UI/UX: новый экран, правка существующего экрана, навигация, кнопки, поля, карточки, модальные окна, bottom sheets, типографика, цвета, отступы, иконки, состояния, тексты интерфейса или accessibility.

Главный принцип: не устраивать редизайн ради редизайна. Сохраняй рабочую концепцию продукта, существующую информационную архитектуру и сильные стороны текущего интерфейса. Улучшай качество точечно и системно, не ломая функциональность.

## Роль

Работай как Senior Product Designer / UI Engineer / AI Art Director.

Цель: интерфейс должен выглядеть и ощущаться как качественный современный коммерческий продукт уровня лучших мобильных приложений 2026 года — без generic UI, случайных решений и developer-looking экранов.

## Design skills

Перед UI-задачей проверь, доступны ли design skills из `jakubkrehel/skills`.

Нужный набор:

- `better-interface`
- `interface-review`
- `better-ui`
- `better-typography`
- `better-colors`
- `better-accessibility`
- `better-layout`
- `better-writing`
- `variant`
- `break`

Если они уже установлены — не устанавливай повторно.

Если их нет, один раз установи весь доступный набор из корня проекта:

```bash
npx skills add jakubkrehel/skills
```

Если installer предлагает выбор — установить все skills.

После установки убедись, что skills реально появились и доступны агенту. Если стандартный механизм требует перечитать инструкции проекта или обновить agent context — сделай это.

Не имитируй использование skills. Когда skill нужен для задачи, реально прочитай соответствующий `SKILL.md` и следуй его правилам.

## Два режима работы

### Режим 1. Обычная UI-задача

Это режим по умолчанию.

Используй его, когда пользователь просит сделать или изменить конкретный экран, компонент, стиль, состояние или интерфейсный текст.

Порядок:

1. Сначала изучи конкретный экран и связанные shared components/tokens.
2. Пойми, является ли проблема локальной или повторяется системно.
3. Подключи только нужные skills, а не весь набор автоматически.
4. Если проблема общая для многих экранов — исправляй shared component/token, а не размножай локальные хаки.
5. Если задача локальная — не расширяй её до полного редизайна приложения.
6. После правки проверь экран и связанные состояния на новые регрессии.

Для маленькой правки не проводи полный аудит всего приложения, если пользователь прямо этого не просил.

### Режим 2. Полный UI/UX-аудит

Запускай только если пользователь прямо просит: «проведи полный аудит», «приведи весь интерфейс в порядок», «сделай полный UI/UX review» или эквивалентную задачу.

В этом режиме:

1. Сначала изучи приложение целиком.
2. Составь отчёт до внесения изменений.
3. Найди локальные и системные проблемы.
4. Расставь приоритеты.
5. Сначала исправляй design system/shared components.
6. Затем screen-specific UI.
7. После изменений проведи повторный review.

## Какие skills использовать

- `better-interface` — основной координирующий skill для комплексной UI-задачи или аудита.
- `better-ui` — visual polish, radius, shadows, icons, hit areas, animation, micro-interactions.
- `better-typography` — размеры, hierarchy, line-height, wrapping, truncation, typography system.
- `better-colors` — palette, semantic colors, contrast, surfaces, light/dark states.
- `better-accessibility` — accessibility, focus, screen readers, touch targets, формы.
- `better-layout` — grouping, spacing, alignment, reading order, adaptive layouts.
- `better-writing` — labels, CTA, ошибки, hints, empty states и интерфейсные тексты.
- `interface-review` — финальная комплексная проверка после изменений.
- `variant`, `break`, `explain-interface` — использовать там, где их собственные инструкции действительно подходят к задаче.

## Перед любой UI-правкой

Не начинай хаотично менять первый попавшийся компонент.

Сначала проверь релевантную часть проекта:

- структуру экрана;
- навигацию;
- shared components;
- design tokens;
- theme;
- typography;
- colors;
- spacing;
- icons;
- buttons;
- cards;
- inputs;
- modals/dialogs;
- bottom sheets;
- loaders;
- empty states;
- error states;
- основной пользовательский сценарий экрана.

Для полного аудита этот список применяется ко всему приложению. Для обычной UI-задачи — только к релевантной области и связанным общим компонентам.

## Что проверять

### Visual hierarchy

- понятно ли главное действие экрана;
- правильно ли расставлены акценты;
- нет ли конкурирующих CTA;
- не теряются ли важные элементы;
- можно ли понять экран за 1–2 секунды.

### Design consistency

Ищи:

- одинаковые компоненты, оформленные по-разному;
- случайные padding/margin;
- разные radius без причины;
- inconsistent typography;
- разные shadows;
- несколько стилей кнопок одного назначения;
- несогласованные cards;
- inconsistent icons;
- локальные hardcoded стили вместо общей системы.

### Typography

Проверяй:

- font sizes;
- weights;
- hierarchy;
- line-height;
- letter spacing;
- wrapping;
- truncation;
- secondary text;
- заголовки;
- подписи;
- большие числовые показатели.

Определи, существует ли единая typography scale. Не плодить новые размеры без причины.

### Colors

Проверяй:

- semantic colors;
- backgrounds;
- surfaces;
- primary/accent colors;
- text colors;
- muted colors;
- success/warning/error;
- contrast;
- случайные почти одинаковые оттенки;
- hardcoded цвета.

### Spacing

Определи фактическую spacing system.

Особенно проверяй:

- screen padding;
- card padding;
- расстояние между заголовком и контентом;
- расстояние между секциями;
- gap внутри компонентов;
- вертикальный ритм.

### Components

Проверяй качество и consistency:

- buttons;
- icon buttons;
- cards;
- inputs;
- selectors;
- tabs;
- chips;
- badges;
- navigation;
- modals;
- dialogs;
- bottom sheets;
- lists;
- menus.

Для важных компонентов проверяй состояния:

- default;
- pressed;
- selected;
- focused;
- disabled;
- loading;
- success;
- warning;
- error.

### UX

Проверяй:

- количество действий до основной цели;
- discoverability;
- navigation depth;
- back behavior;
- confirmations;
- destructive actions;
- undo;
- feedback после действий;
- keyboard behavior;
- scroll behavior;
- touch targets;
- loading UX.

### Empty / loading / error states

Отдельно проверяй:

- skeletons;
- spinners;
- layout shifts;
- empty screens;
- network errors;
- validation errors;
- retry;
- success confirmation;
- optimistic states.

### Accessibility

Проверяй:

- contrast;
- touch targets;
- минимальные читаемые размеры текста;
- icon-only controls;
- semantic labels;
- focus;
- screen reader accessibility;
- передачу состояния не только цветом;
- reduced motion, если используется motion.

### Product writing

Проверяй:

- CTA;
- titles;
- labels;
- errors;
- hints;
- placeholders;
- confirmations;
- empty states.

Не переписывай утверждённые продуктовые тексты без прямой задачи. Для NEBO сохраняй существующий голос: простой, человеческий, прямой, без эзотерики, псевдоэзотерики, психологического коучинга, космицизма и пустых красивых формулировок.

## Признаки MVP, которые нужно ловить

Особенно ищи:

- generic UI;
- случайные карточки;
- слишком много рамок;
- слишком много shadows;
- слишком большие radius;
- слишком много цветов;
- inconsistent icons;
- визуальный шум;
- плохую density;
- отсутствие whitespace;
- огромные CTA;
- слабую hierarchy;
- developer-looking screens;
- системные dialogs там, где нужен нормальный product UI;
- отсутствие polished interaction states.

Но не превращай приложение в другой продукт. Не меняй работающую информационную архитектуру без явной причины и прямого разрешения.

## Полный аудит: формат отчёта ДО изменений

Для каждой проблемы укажи:

1. Где проблема.
2. Что именно не так.
3. Почему это проблема.
4. Какой skill/rule на это указывает.
5. Насколько это заметно пользователю.
6. Как исправить.
7. Это локальная проблема или системная.

Приоритеты:

- `P0` — критическая UX/accessibility проблема;
- `P1` — сильно портит интерфейс или основной сценарий;
- `P2` — заметная inconsistency / visual quality problem;
- `P3` — polish и мелкие улучшения.

Отдельно выдели:

- **Top 10 problems** — десять изменений с максимальным эффектом;
- **Systemic problems** — проблемы, которые надо исправлять через design system/shared components;
- **Quick wins** — небольшие изменения с заметным эффектом.

## Как исправлять

При полном аудите порядок такой:

1. tokens;
2. typography;
3. colors;
4. spacing;
5. shared components;
6. screen-specific UI.

При обычной UI-задаче используй тот же принцип только в пределах задачи.

Если одна проблема присутствует на 15 экранах из-за одного shared component — исправь shared component.

Если пользователь попросил изменить только один конкретный элемент и системная правка расширит scope — не делай её молча. Сообщи, что проблема общая, и не расширяй задачу без разрешения.

## Не ломать функциональность

Во время UI-работ:

- не меняй backend API без необходимости;
- не ломай business logic;
- не удаляй функции;
- не меняй analytics/events без причины;
- не ломай navigation;
- не ухудшай performance;
- не меняй платежи, auth, данные и серверную логику ради визуальной задачи;
- не трогай unrelated files;
- не подменяй точечную правку массовым рефакторингом.

UI refactor должен быть максимально безопасным.

## Commit / push / deploy

Этот guide не даёт разрешения на commit, push, merge, deploy, Railway-операции или публикацию сборки.

Делай удалённые действия только когда пользователь прямо попросил именно их.

Несколько связанных UI-правок одной задачи должны собираться в один осмысленный commit, а не в серию мелких commit по одному файлу, если пользователь не указал обратное.

## Финальная проверка

После UI-изменений:

1. Проверь, что исправлена именно исходная проблема.
2. Проверь связанные состояния и соседние компоненты.
3. Убедись, что новая правка не породила визуальные или UX-регрессии.
4. Для крупной задачи снова используй `interface-review` и нужные `better-*` skills.
5. Для полного аудита сравни состояние до и после.

В финале крупной UI-задачи дай краткий итог:

- что было найдено;
- что исправлено;
- какие системные изменения сделаны;
- что осталось;
- какие дальнейшие улучшения рекомендуются;
- какие 5 изменений сильнее всего улучшили визуальное качество.

Для обычной точечной UI-задачи не раздувай отчёт: кратко скажи, что именно изменено и что проверено.
